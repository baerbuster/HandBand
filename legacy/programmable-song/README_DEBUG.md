# Programmable Song – Debugging Clicks  
`README_DEBUG.md`

This guide explains how to use the special **debug versions** of the synth library and sequencer GUI to track down the *click* you hear at the end of certain short notes.

---

## 1 . What’s in this folder?

| File | Purpose |
|------|---------|
| **synthlib_debug.cpp** | C++ PortAudio synth with extensive debug logging. |
| **ProgrammableSong_debug.py** | Python GUI/sequencer that drives the debug synth and writes its own log. |
| **libsynth_debug.so** | Shared library produced from `synthlib_debug.cpp` (created after compilation). |
| `debug_logs/` | Folder automatically created by the Python program; contains time-stamped log files. |
| **README_DEBUG.md** | *This* document. |

---

## 2 . Prerequisites

* C++17 compiler (`g++` ≥ 7 recommended).  
* [PortAudio](http://www.portaudio.com/) development headers & libs.  
* Python 3.9+ with Tkinter (usually included) and `ctypes`.  

> macOS (Homebrew) example for PortAudio:  
> `brew install portaudio`

---

## 3 . Build the debug synth

From **Desktop/Programmable Song**:

```bash
g++ -std=c++17 -fPIC -shared synthlib_debug.cpp -o libsynth_debug.so \
    -I/opt/homebrew/opt/portaudio/include \
    -L/opt/homebrew/opt/portaudio/lib -lportaudio -pthread
```

Adjust include / lib paths if PortAudio is installed elsewhere.

Successful build yields **libsynth_debug.so** in the same directory.

---

## 4 . Run the debug sequencer

```bash
python ProgrammableSong_debug.py
```

The first run creates a `debug_logs` folder and two rolling logs:

* `synth_debug.log` – low-level audio-side info (generated by C++)  
* `sequencer_debug_<timestamp>.log` – high-level events (generated by Python)

---

## 5 . Using the GUI

1. **BPM slider** – real-time tempo change (logarithmic 80 – 180 BPM).  
2. **Test Patterns** – radio buttons switch between predefined note-length patterns (single-step, two-step, etc.).  
3. **ADSR Envelope** – if your build exports the extra setters you can tweak Attack/Decay/Sustain/Release and immediately hear/see the effect in the logs.  
4. **Debug Tools**  
   * *Analyze Click Patterns* – scans stored note durations & BPMs, flags suspiciously short notes.  
   * *Clear Note History* – resets collected statistics.

The status bar at the bottom mirrors important runtime events.

---

## 6 . Interpreting the logs

### 6.1 `synth_debug.log` (C++)

Look for these markers:

* `NOTE_ON` / `NOTE_OFF` – when the GUI issues on/off.  
* `TRANSITION DETECTED` – point where the note state flips.  
* `LARGE AMPLITUDE JUMP DETECTED` – **smoking gun** for a click: two adjacent samples differ by >0.1 (change the threshold in the file if needed).  
* Envelope stage prints (`ATTACK:`, `DECAY:`, `SUSTAIN:`, `RELEASE:`) show per-sample multipliers.  
* At `NOTE_OFF`, the code prints which stage the note ended in (ATTACK/DECAY/SUSTAIN) – if you consistently see “ATTACK” or “DECAY” before clicks, the premature envelope cut-off is confirmed.

### 6.2 `sequencer_debug_*.log` (Python)

Contains:

* Step-by-step sequencer timeline with BPM.  
* Each note’s exact duration (ms) and its BPM context.  
* Summaries per measure and per BPM group.  
* Warnings produced by `analyze_clicks()` for BPM ranges with extremely short notes.

Cross-reference the timestamps of `NOTE_OFF` in `synth_debug.log` with the durations in `sequencer_debug_…`. Short notes ending inside ATTACK/DECAY almost always line up with the clicks.

---

## 7 . Typical investigation workflow

1. Build `libsynth_debug.so`.  
2. Start **ProgrammableSong_debug.py**.  
3. Pick the **Single Step** pattern and set a **high BPM** (e.g. ≥160). Listen for clicks.  
4. Stop the GUI (window close).  
5. Open `debug_logs/synth_debug.log`.  
   * Confirm `LARGE AMPLITUDE JUMP` lines near each click you heard.  
   * Note which envelope stage `NOTE_OFF` occurred in.  
6. Repeat with slower BPM or longer patterns. Compare logs; clicks should disappear when `NOTE_OFF` occurs during SUSTAIN or after a full attack/decay cycle.  
7. Adjust envelope lengths (GUI sliders) and reproduce steps 3-6 until you can demonstrate the relationship between **premature envelope cut-off** and audible clicks.

---

## 8 . Cleaning up

To start a fresh session, simply delete the `debug_logs` folder or its contents; they will be recreated automatically.

---

## 9 . Next steps

Once the root cause is confirmed you can:

* Shorten the attack or lengthen the release so the amplitude always returns to 0 smoothly before the buffer finishes.  
* Cross-fade the envelope when a new `note_on` arrives during the previous `note_off`.  
* Add a click-free *minimum note length* rule in the sequencer.

Happy debugging — and may your sine waves end smoothly!
